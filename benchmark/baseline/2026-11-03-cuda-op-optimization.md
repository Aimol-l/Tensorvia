## 改了什么

- **归约**（`reduce.cu`）：`inner == 1` 的轴归约改成 block 协作（一个 block
  一个输出、线程沿归约轴分摊），全归约趟 1 从"每 block 一个线程串行走一段"改成
  "每 block 256 线程合并读一段 + 树形归约"。
- **转置**（`transpose.cu`）：32×32 共享 tile 内核参数化为"批次 × 行 × 列 +
  输入/输出行步长"，二维交换是 batch=1 的特例；rank-3 的六种置换按"输出连续轴
  是否与输入连续轴同向"分流到连续拷贝或共享 tile 转置。通用 div/mod 内核保留为
  兜底。
- **矩阵乘**（`matmul.cu`）：16×16/每线程 1 输出 → 64×64/每线程 8×8、kBlockK=32
  的寄存器分块；64-tile 不足 32 个时（如 256³ 只有 16 个）退回 16×16 内核。
- **卷积**（`conv.cu`）：3×3 走寄存器缓存路径（每通道把 6×6 输入窗收进寄存器，
  4 个输出通道共用）；通用 kh/kw≤5 走共享 patch + 输出通道分块；更一般的形状
  保留原逐元素内核。
- **归一化**（`norm.cu`，新增）：每行一个 block，行驻留共享内存（≤48 KB），
  均值/方差/仿射三趟只读一次全局；超限时退回流式两遍。

## 采集说明与已知偏差

- 单卡无其它计算任务；即便如此，偶发运行仍会出现 1.5~2× 的离群（同一次运行里
  多个无关用例一起变慢，随后恢复），所以取 3 次运行中位数，不取单次。
- 改前数字用 `git show HEAD:src/backend/cuda/device/<file>.cu` 临时替换后实测；
  每个值取两次运行中较慢的一次，所以表里的加速比偏保守。替换后已还原，工作区里
  是优化版。
- `layer_norm` / `rms_norm` 的改前值是临时把 `src/core/ops.cpp` 的 CUDA 派发
  短路（`false &&`）强制走 `*_composed` 组合路径测的，测完已还原。
- 未重测的用例（逐元素、where、gather、index_select 等）代码路径未动，首版
  基线的数字仍有效。
- `arange` / `randn` 是宿主生成后搬运的既有设计（`tools/coverage_overrides.toml`
  标为 host_side），本次未改；它们的 ~9 GB/s 不代表设备内核性能。

## 未追求的方向

- **matmul 128×128 tile**：实测更慢（1024 时 8.7 TFLOPS vs 11.4），原因是每线程
  64 个累加器的寄存器压力把占用率压到 2 block/SM；已回退。
- **matmul 与 cuBLAS 的差距**（11.4 vs 同机约 20.7 TFLOPS）：剩余空间要靠
  `cp.async` 双缓冲 + 128-bit 共享读 + 更大 tile 重写，收益不确定、回归风险高，
  当前已远超 8% 的合同下限。
- **conv 通用路径的寄存器缓存**：测例只覆盖 3×3；通用路径已有共享 patch，继续
  优化无法用现有 bench 验证。
- **transpose3d 再提速**：364.85 GB/s 已是 memcpy 的 61%，tile 内没有明显浪费。

## 正确性

- `mcpp test --features cuda ...`：11 个可执行全部通过，4 个 MultiDevice 用例
  因单卡环境跳过（既有）。
- 新增 rank-3 六种置换（3×5×7 非方阵）与 rank-4 置换的转置对照测试。
- 过程中发现并修复 CPU `Transpose` 的既存 bug：`transpose_nd_kernel` 的
  "prefix + 递归"快路径对 `axes[0] != 0` 的 rank≥3 置换会退化成恒等拷贝
  （`{1,0,2}`、`{2,0,1}` 等）；现已改为逐元素重排兜底。修复前该函数给出的结果
  与 API 约定不符，新测试正是以它为参考才暴露出来。
